# Provider and deployment reference

## Provider setup

Google OAuth uses authorization code, PKCE and a single-use session-bound state. Register the console origin followed by `/api/oauth/google/callback` in the Google client. Configure the client ID, secret and scope through the console. Gmail page reads require explicitly authorized label IDs. The Google Sheets connector restricts requests to selected spreadsheet IDs. For a read-only Revolut credential, supply account IDs. Twilio accepts `accountSID:authToken`. Supabase Database takes a JSON credential with `project` and `key`, and an explicit list of table names. The public briefing adapter does not send credentials upstream. GitHub also accepts a JSON credential with app_id, installation_id, private_key and an explicit repository_ids list for read-only installation tokens. Reddit accepts client_id, client_secret and user_agent. Bluesky accepts identifier and app_password. In those modes the broker obtains the short-lived provider token at dispatch. Other token-based integrations take the upstream access token or API key. Provider-specific scopes, account entitlement and test accounts determine which upstream calls succeed.

## Operations


Every command in this guide says who runs it, on which machine, and whether it needs sudo.
The broker binds to 127.0.0.1. The console unit binds to 127.0.0.1 explicitly (`next start -H 127.0.0.1 -p 3000`): `localhost` can resolve to `::1` with Node 24, and the proxy, the console rewrites and the installer all dial 127.0.0.1. Use a TLS reverse proxy for remote access and publish only the intended surfaces. `OPENPASSWORD_HOME` selects the data directory. `OPENPASSWORD_PORT` changes the broker port and the console rewrite destination. Set it consistently at build and start. `OPENPASSWORD_WEB_ORIGIN` must match the browser origin. Enable the optional YouTube chunk relay with `OPENPASSWORD_YOUTUBE_RELAY=1`. Provider keys are entered via the console, without provider environment variables.

Keep the SQLite database and master.key together in a protected backup. For an offline backup stop the service, copy the complete data directory including SQLite sidecars, and preserve file permissions. The default deployment uses a local master key and process-level trust. Use a dedicated service user with a private home. Protect the operator token during initial setup. The local launch and storage layout are designed for Linux including ARM64. The service has been tested on Linux x86-64.

## Request limits

Two limits protect the broker. Neither replaces a firewall: put per-source connection-rate limits (for example nftables) on ports 80 and 443 for flood protection.

- **Per source address, on sign-in and pairing paths.** `/admin/login`, `/auth/*` starts and setup, `/v1/hosts/enroll`, `/v1/device/authorizations`, `/v1/device/token` and `/v1/delegation/check` allow 60 requests a minute per source address and path (a device path with a valid host proof is keyed by its host, 2400 a minute). Over the limit returns 429. Behind a reverse proxy every client reaches the broker from the proxy's address, so the limit would be shared by all clients. Set `OPENPASSWORD_TRUST_PROXY` to the proxy's address, for example `127.0.0.1` (comma-separated addresses or CIDR ranges of at least 8 bits; unset by default). The broker then reads the client address from `X-Forwarded-For` only when the connection comes from a listed proxy; a forwarded address from any other peer is ignored. Wildcards, hop counts and ranges that would trust the whole internet are refused at start. The proxy must overwrite, not pass through, a client-supplied `X-Forwarded-For`.
- **Per grant, on every authenticated `/v1` request.** One grant may make `OPENPASSWORD_GRANT_RATE` authenticated requests a minute (default 600; only an explicit `0` turns it off, with a warning at start; an empty, blank or malformed value stops the broker from starting). Over the limit returns 429 `Try again in one minute`. A request with a bad or expired credential is refused as before and does not use a grant's budget. Counters are in memory and restart with the broker.

## Backups

The data directory holds `vault.sqlite` (encrypted provider credentials, grants, history), `master.key` (the key for those credentials) and `operator.token`. A database copy alone retains readable metadata but cannot decrypt broker-sealed values without the associated master key, and a copy of both together must never be stored unencrypted off the host. `deploy/backup/backup.sh` therefore writes both into one **borg** archive, encrypted on the host before upload; only the encrypted archive leaves it.

### Encrypted backup with the operator's key (nothing to decrypt it on the host)

Use this where the operator holds the key and the host must not. The snapshot holds the vault and `master.key` in plain form (sealed provider values are encrypted under the master key, but titles, usernames, grants and audit metadata are readable, and `master.key` and `operator.token` are plain unless a wrapping key is in use), so it is encrypted on the host to the operator's **public** age key before it leaves. The host holds only that public key: it can encrypt, never decrypt.

For an operator who is not a command-line user, `deploy/backup/operator-backup.sh` does both operator steps in one file: `bash operator-backup.sh init` creates the key pair (private key in `~/.openpassword-backup`, never printed) and shows only the public line to hand over, and `bash operator-backup.sh check FILE.age` opens a backup file, prints table names and row counts only, deletes the opened copy and ends with `RESTORE CHECK PASSED`. Run it as a file; never paste it into a terminal. It needs `age`, Node 24 and `tar`, and sits next to `restore-encrypted.sh`. Backup files (`.age`, ciphertext) reach the operator at a location the person with server access names when handing them over; they are never sent by email. The manual steps follow.

One-time, by the operator, on his own machine: install `age` from the distribution package, run `age-keygen -o openpassword-backup.txt`, keep that file private (mode 0600, offline copy; it may be passphrase-protected with `age -p`), and hand over only the public line printed by `age-keygen -y openpassword-backup.txt`. The person with server access installs `age` from the distribution package on the host (pin and record the installed package version in the deployment notes) and writes the public line to `/etc/openpassword/backup.recipient` (a regular file, not a symlink, owned by the user who runs the backup and not writable by group or others; only `age1…` lines and comments are accepted, and a private key is refused). The file is read once, validated, and the validated keys are handed to `age`. Do not create `backup.env` and leave `openpassword-backup.timer` disabled.

A backup, by the person with server access, run on the server with sudo and redirected into a file owned by their own account: `sudo /opt/openpassword/current/deploy/backup/backup.sh --encrypt > openpassword-YYYYMMDDTHHMMSSZ.age`. Stdout is the ciphertext and nothing else, and a non-zero exit means it is not a backup, so write to a file and delete it on failure: `... > f.age || rm -f f.age`. The script refuses a terminal, a missing or bad recipient file and a missing `age` before any snapshot is taken. The plain snapshot never touches a disk. As root, the snapshot and the encryption both run inside one transient systemd unit whose runtime directory is a tmpfs that systemd removes when the unit stops, so only ciphertext returns to the script; cancelling the script stops that unit and waits for it before returning. With `--direct` (not root) it is staged on a tmpfs or ramfs (`$XDG_RUNTIME_DIR` or `/dev/shm`, or `OPENPASSWORD_BACKUP_STAGE`) and nowhere else. Both refuse unless the memory is safe: tmpfs is memory that Linux may swap, so the script refuses when any swap device is neither encrypted (dm-crypt) nor zram, unless the mount has `noswap`. Turn swap off or encrypt it on the host. The snapshot unit runs `deploy/backup/unit-run.sh` rather than an inline script, because `systemd-run` expands `$VARIABLE` and `%specifier` in the arguments it passes; `backup.sh` refuses paths containing `$` or `%`. `make backup-age-test` proves the refusals and the cleanup after success, refusal, failure and termination (Linux, needs age); `make backup-age-systemd-test` proves the root path on a staging host with a disposable vault; run it as root directly, not through sudo, because under sudo the backup script ignores the settings the test passes. `make backup-age-test` runs it when it is root on a systemd host. The `.age` file is safe to move by any channel. To run it from a restricted ssh key instead of a shell, use a dedicated account that owns nothing else: `useradd --system --no-create-home --home-dir /nonexistent --shell /bin/sh openpassword-backup` (no password), and keep the key file in a root-controlled place instead of the account's home: in `/etc/ssh/sshd_config` add `Match User openpassword-backup` with `AuthorizedKeysFile /etc/ssh/authorized_keys/%u`, `PasswordAuthentication no`, `AllowTcpForwarding no` and `X11Forwarding no`; create `/etc/ssh/authorized_keys` (root:root, 0755) and `/etc/ssh/authorized_keys/openpassword-backup` (root:root, 0644), so every component of the path is root-controlled and the account cannot change its own key or forced command. The file holds one line `command="sudo -n /opt/openpassword/current/deploy/backup/backup.sh --encrypt",no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding,restrict ssh-ed25519 AAAA… backup-transport`, and one sudoers rule in `/etc/sudoers.d/openpassword-backup` (mode 0440, checked with `visudo -cf`): `openpassword-backup ALL=(root) NOPASSWD: /opt/openpassword/current/deploy/backup/backup.sh --encrypt`. The rule names the exact arguments, so the account cannot run any other mode or script. Keep sudo's default `env_reset` and do not add `SETENV` or `env_keep` for `OPENPASSWORD_*`; in addition `backup.sh` ignores every `OPENPASSWORD_*` setting when it runs under sudo (`SUDO_USER` set) and uses its defaults, and its test substitutes (age, swap table, sysfs) are honored only when a `.test-seams` file sits beside the script, which a release never contains. Reload sshd and test it with a command other than the forced one before relying on it. The recipient file is then owned by root and read by the root run. That key can only produce ciphertext. Swap policy detail: zram swap is accepted only when its `backing_dev` is `none` (or not configured), because a zram device with a writeback device can write pages to that disk.

Restore, by the operator, on his own machine, as his own account (no sudo), one script: `OPENPASSWORD_BACKUP_IDENTITY=~/openpassword-backup.txt deploy/backup/restore-encrypted.sh openpassword-YYYY….age ./restored`. It decrypts into a scratch directory and examines the archive before extracting anything: it must hold exactly regular files named `vault.sqlite`, `master.key` and optionally `operator.token`, each once; links, directories, extra or duplicate members and path tricks are refused. It then checks the vault's integrity and fills the empty target only when everything passed; a wrong key, a damaged file or an unexpected archive leaves the target empty. Set `OPENPASSWORD_NODE` to a Node 24 binary if `node` on his machine is older. The operator may also store the `.age` files in his own borg repository with his own key (`borg create ::name file.age`); the key never reaches the host. Prove one restore before enrolling real credentials, and take a backup before every upgrade.

### Host-held backup key (optional)

Setup, once, as root. Create `/etc/openpassword/backup.env` (owner root, mode 0600) with `BORG_REPO` (for example an `ssh://` repository on your storage), `BORG_PASSCOMMAND` (a command that prints the passphrase, such as `cat /etc/openpassword/backup.pass` with that file at mode 0600) and optionally `BORG_RSH` for the SSH key and port. `BORG_PASSPHRASE` in the file is refused. Initialise the repository with `borg init --encryption=repokey-blake2` using the same settings. Keep the passphrase and a copy of the repository key somewhere other than the backed-up host: without them an archive cannot be opened.

On the server as root, run `deploy/backup/backup.sh`. It takes a consistent snapshot with SQLite's online backup (safe while the broker runs), under the broker's own service identity so that it cannot change file ownership in the state directory, then runs `borg create`. `--direct` runs as the user that owns the data directory (used by the tests and for local installs). `deploy/systemd/openpassword-backup.service` and `.timer` run it daily; install them like the other units and enable the timer. The scripts use the bundled Node (`OPENPASSWORD_NODE` overrides the path).

To restore, as the account that owns the `backup.env` file (root in the setup above), on the server or a recovery machine that has it, run `deploy/backup/restore.sh <archive-name> <empty-dir>` (find names with `borg list`). It restores into an empty directory, never over a live one, and checks that the vault passes SQLite's integrity check. To bring a host back: stop both services, move the restored files into the state directory with their ownership as before, start the broker, then the console. Practise a restore before relying on the backups. In a checkout on a Linux test machine, as an ordinary account (no sudo), `make backup-test` exercises backup and restore against a local borg repository (Linux, needs borg).

## Sign in to another application

Under **Workspace → Register app**, enter the application's exact HTTPS callback and audience. Activate its registration. A signed-in workspace member can confirm an identity-only handoff at `/delegate` with a one-use S256 challenge. The confirmation page may redirect only to the registered callback's origin, whose host must be a domain name or IPv4 address (letters, digits, hyphens and dots); registration refuses any other. Have the callback answer on that origin: the browser can block a further redirect from it to another origin. The application backend exchanges the returned code at `/delegate/exchange` and verifies the Ed25519 signature against its pinned key. The public key document is available at `/.well-known/openpassword-jwks.json`. Identity-only grants expire within ten minutes. Applications can also register action classes. The owner receives a one-time checker credential. The application exchanges a code, rotates the refresh credential and checks each action against POST /v1/delegation/check. A repeated refresh revokes its grant. POST /delegate/status checks identity-only delegations, including those issued by a recently retired key. Owners rotate the signing key with POST /admin/delegation/signing-key/rotate.

### Issue bundles and dispatch controls

Enroll a HubSpot connection with each permitted template directory and one upload folder as selected resources. The upload folder is the entry that starts and ends with `/`, for example `/example-newsletter/`: up to five segments of letters, digits, `_`, `.` and `-`, each starting with a letter, digit or `_`. A connection with no such entry, or more than one, cannot publish issue bundles. Each bundle is uploaded to a subfolder named after its issue ID. A connection enrolled earlier with an absolute folder keeps using it. Issue the device a grant for `hubspot.files.upload_bundle`. Stage each image at `POST /v1/hubspot/issue-assets` with its original media type and the query fields `connection_id`, `file_name` and `sha256`. Invoke the operation with the returned file manifests, issue ID and bundle digest. The owner can review the upload destination, draft changes and exact manifest before dispatch. Read durable per-step receipts at `GET /v1/hubspot/issues/:id?connection_id=…`. Each issue ID can be reserved once per connection. The public service uses explicit workspace, connection, grant and folder selection in place of the private deployment’s hard-coded organization and portal.

Workspace owners can pause a single operation under **Workspace → Provider dispatch controls**. An upgrade from v0.1 expires outstanding YouTube relay proofs because they lack the operation identity needed for pause enforcement. Request a fresh upload session for an interrupted relay. Revolut transaction reads now require a selected account ID, including the legacy list alias. Supabase table selection permits columns from the selected table and explicitly scoped row writes.

### Personal profiles and sign-in methods

At first launch you can also expand **Create administrator with social sign-in**. Enter the installation setup code and the provider's OAuth web application credentials. Successful authorization creates the owner profile. A password is optional.

Under **Workspace → My profile**, owners, editors and viewers can add or change their username and password, link a configured Google, GitHub or Apple account, and remove individual methods. Each identity belongs to one profile. Linking requires a signed-in session. A workspace member can use their issued access token to enroll. The owner's **Authentication** settings configure the provider applications for the installation. Removing a provider is blocked if a profile depends exclusively on it.

For Apple, configure a Services ID, register the HTTPS domain and the displayed return URL in Apple Developer, and enter a signed Apple client-secret JWT. Rotate the JWT before expiry using the same Services ID. Local installations need a registered HTTPS domain for Apple. Password sign-in works on loopback.

### Credential ownership and sharing

Each workspace is an organization boundary. **Connections** lists the provider accounts you can use, with their source: **Organization**, **Owned by you**, or **Shared by** a named owner. The grant picker uses the same connections. Agent access uses scoped, expiring device tokens; the provider secret stays in the broker.

Only the administrator can add an organization credential. It is available to the entire workspace. Any active member can add a personal credential, which starts private. The owner can use **Edit access** to rename it and share with specific active people or everyone in that workspace. Rotation and revocation belong to the credential owner; the administrator manages organization-owned credentials. Sharing a personal credential with everyone preserves its personal ownership.

Removing someone's access invalidates agent grants they issued for that credential. Restoring sharing requires a new grant. Removing a member invalidates grants issued by that member and grants against that member's personal credentials. Existing installations migrate previously workspace-wide connections to organization ownership. Sign-in methods and human vault items use their existing access rules.

### Credential and sharing expiry

Set **Credential expiry** when connecting a provider or later under **Connections → Edit access**. A blank field gives the connection no OpenPassword deadline. For named sharing, each recipient has a separate deadline. **Whole-organization sharing expiry** limits organization-wide access. The owner retains access until the credential itself expires. All fields accept a UTC date and time and include an **In 7 days** shortcut.

A device grant ends at the earliest of its requested expiry, the credential deadline, and its issuer’s applicable sharing deadline. Shortening a deadline caps existing grants. Extending it permits new grants without extending previously issued ones. These deadlines control use through OpenPassword. A provider can expire or revoke its underlying key independently.

### Consumption

Open **Consumption** to inspect provider requests by credential or agent grant, with a period selector and paginated event history. Usage is attributed to the grant the caller presents. Give each agent a distinct grant when you want separate permissions or usage history. The issuing profile sees its usage; credential owners can also see consumption through their credentials. Organization-owned connections are visible to the administrator.

The SQLite ledger records each outbound HTTP attempt made by a brokered connector operation, model chat completion or YouTube upload relay before dispatch. Each attempt retains the timestamp, credential ID and revision, provider, device grant and label, issuing profile, operation and outcome. Retries that contact a provider count again. Cached replays and broker-only requests add no upstream event. A crashed or incomplete attempt remains visible with an unresolved outcome. A successful HTTP status describes the upstream response; it does not prove a billable operation completed.

Model usage is captured from JSON and streaming usage frames even without a tariff. Optional grant tariffs calculate USD estimates from reported usage. The report joins existing settlement and reconciliation records and shows unsettled reservations separately. Missing usage or pricing remains unpriced. Counts and totals begin with deployment of the ledger. The deployment's existing vault backup includes the ledger. Provider invoices, native Claude Code/Codex sessions and API calls outside the supported broker routes require separate ingestion.

## Release package

As an ordinary account (no sudo), on a Linux host with Node 24.19.0 as the build Node (the release refuses any other version), `xz`, and network access to nodejs.org, check out the exact commit to release and run `make package COMMIT=<sha>`, then `make checksum`. `make package` refuses a dirty tree or a different HEAD, builds that commit in a scratch directory from `git archive`, keeps only production dependencies and the runtime files, and writes `dist-release/openpassword-<version>-linux-<arch>.tar.gz`, `RELEASE.json` (commit, tree, Node version and binary hash, lockfile sha256, source epoch) and a completion marker. `make checksum` writes the `.sha256` sidecar only for an archive that matches its marker and `RELEASE.json`. Two builds of the same commit and toolchain are reproducible except for the per-build files listed in `scripts/per-build-files.txt` and in `RELEASE.json` (`per_build_files`): Next.js generates a secret server-reference key on every build, which must differ per build and is never made deterministic. `make package` also writes `<name>.manifest`, the sha256 of every other file, and `scripts/compare-builds.sh <dirA> <dirB>` compares two manifests. Build diagnostics (`.next/trace`, `.next/diagnostics`, `.next/cache`) are not shipped. It includes built output and installed dependencies, so build it on the target architecture. ffmpeg and Chromium are not included.

`make package` refuses to build when `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` is set in the environment, because Next.js embeds a caller-supplied key in the build output; the generated key stays random per build. It also refuses unless every per-build file exists as regular files in the staged release. The only per-build paths are `.next/server/server-reference-manifest.json` (the generated key described below; its `.js` companion showed no variance and is compared) and `.next/server/preview-props.json` and `.next/prerender-manifest.json` (Next's random preview-mode keys, diagnosed in the 4fd28b31 gate diff). `make package` builds in the fixed directory `/tmp/openpassword-release-build` and refuses if it exists, before changing anything, and holds it until the build ends; the directory and `dist-release/` are created owner-only (0700) because they hold per-build key material. It builds there because Next embeds absolute build paths and derives module ids from them, which made two builds in different checkouts differ (also diagnosed in that diff); the first two-build run must confirm they are the only legitimate differences. The server-reference files hold the key Next generated for that build, which the server needs at run time to encrypt Server Action closures. It is random, belongs to no operator, and protects no credential or vault data. Do not substitute your own key at build time. No server action exists in the source today, so that key protects none. `make package` also refuses to build if `app`, `server` or `packages` mention Server Actions or preview/draft mode (`use server`, `draftMode`, `setPreviewData`, `previewData`, `__prerender_bypass`). **The release archive is not a public download.** It also contains Next's random preview-mode values, which the locked Next.js runtime loads at run time; a public archive would disclose the same values to everyone running that build. Do not attach it to a public release. It stays in gate custody and installs are made from there, until a distribution design with per-install keys, or with the framework behaviour disabled, has been qualified. This is the maintainer's reading of Next.js behaviour and is unverified until the gate inspects the built archive.

Deploy the private gate artifact using the archive updater below.

## CLI enrollment and live activity

The installation setup code is read on the server and entered in the browser. For a pre-existing standalone workspace, create a grant in the target workspace and choose **One-time CLI enrollment token**. The server stores a digest of this ticket. Redeeming it consumes the ticket and issues the device credentials in one SQLite transaction. Existing paired devices can continue to refresh their credentials. If the client loses the response during enrollment, revoke that grant and issue a new ticket.

Use the CLI download served by the installation. Set `OPENPASSWORD_BROKER` and `OPENPASSWORD_AGENT` in the environment of both the CLI and its MCP process. Compare `openpassword whoami` with the ID under **Access grants**. The **CLI connected** timestamp records redemption. An MCP `whoami` call verifies which grant the running harness is using.

The browser long-polls `/api/admin/activity` with its authenticated session. Owners see the selected workspace; members see their own audit actions. The agent endpoint `/v1/activity` returns only events attributed to the authenticated grant. Both return the latest 100 visible events in chronological order on first contact. Pass `after=<last-id>` to read subsequent pages. An idle request waits up to 20 seconds. A timeout returns an empty page and preserves the cursor. To resume a CLI stream, run `openpassword watch LAST_EVENT_ID`.

Keep the reverse proxy's response timeout above 20 seconds. Each broker process caps pending polls at 4,096 total and 512 per audience. A full group returns HTTP 429. SQLite retains the audit events across disconnects and restarts. Wake notifications are local to one broker process. The separate consumption ledger tracks provider requests and usage.

To reproduce the gateway load checks, in the project root on a development machine as an ordinary account (no sudo), run `node --import tsx scripts/gateway-load.ts --minute` for 3,000 scheduled chat requests over one minute or omit `--minute` for a 40-client burst. Both use loopback HTTP, a disposable SQLite vault and a simulated upstream. The check verifies dispatches, saved requests, consumption records and the grant's activity cursor.

## Upgrade a running systemd installation

The release signer supplies the detached CLI signature as described in [SECURITY.md](../SECURITY.md). The Linux gate uses Node v24.19.0, runs the test suite, builds the exact commit with `make package COMMIT=<full-sha>`, then runs `make checksum`. Record the approved **archive digest, commit, version and architecture** independently of the file transfer. Keep the archive in gate custody.

On the server use the trusted `deploy/upgrade.sh` delivered separately with the gate handoff. Linux, GNU tar/coreutils, util-linux flock and systemd are required. Production needs neither npm nor a checkout. For example, with the gate's values in the shell:

**Run as:** your own account through sudo (the script requires root) · **Where:** the production server · **sudo:** yes

```sh
sudo sh deploy/upgrade.sh --install "$ARCHIVE" "$EXPECTED_SHA256" "$VERSION" "$EXPECTED_COMMIT"
```

Set the broker unit's environment drop-in to `OPENPASSWORD_WEB_ORIGIN=https://vault.example.com` (your console's public origin) for this deployment, and, when the reverse proxy runs on the same host, add `OPENPASSWORD_TRUST_PROXY=127.0.0.1` so the sign-in and pairing limits are per client address instead of one shared bucket (see Request limits). Use the existing reverse proxy. For a nondefault local console port pass `OPENPASSWORD_WEB_PORT` through sudo. The existing vault, master key, sessions and grant records remain in the broker's state directory.

The installer hashes a private staged copy before extraction, then runs the verified release's TypeScript upgrader using its bundled Node. It checks release identity and Node digest, installs the release at `/opt/openpassword/releases/<version>`, and exercises the broker on a disposable vault and the Next launcher under a transient service identity. A previously installed version is reusable only with the same recorded archive digest. Reusing a version from a manual install without a receipt is refused; use a new version.

The activation lock covers preflight through readiness. A supporting broker gets up to 90 seconds to drain. Older brokers use their existing shutdown behavior. Both services stop, and the updater then takes a copy of the state directory (see below). When they stop, systemd also stops units of yours that carry that stop, such as an HTTPS ingress with `Requires=openpassword-web.service` (also `Requisite=`, `BindsTo=`, `PartOf=` and `StopPropagatedFrom=`, or `PropagatesStopTo=` in a drop-in on the OpenPassword unit; `Wants=` and `After=` do not). Just before stopping, the updater records in its journal which of those are running, and starts them again once the services are back, including after a rollback or `--recover`. If a public start fails they stay stopped until `--recover` succeeds. If the services come back but one of these units does not start, the command fails and the activation stays pending; fix the unit and run `--recover`, which leaves healthy services running and starts what is still down. The candidate is proven before it is public: it replaces the `current` symlink and base units, the broker alone starts on private port 4151 through a runtime drop-in under `/run` (gone after a reboot), against the real store, which it may migrate, while the console stays stopped. Its health and release identity must agree. It then stops, and rollback is disarmed: the journal is marked committed before the normal-port start, because from then on the broker can accept writes. The public start runs both units with local console and broker readiness, service working directories and bundled executables. A failure there is fixed forward; `--recover` repeats the public start. Drop-ins are preserved. On first installation enable both units for boot after successful readiness.

Use the **installed version that contains this updater** as the argument to these maintenance commands, even when the active version is older:

**Run as:** your own account through sudo · **Where:** the production server · **sudo:** yes

```sh
sudo sh deploy/upgrade.sh --rollback 0.4.0
sudo sh deploy/upgrade.sh --recover 0.4.0
```

The state copy is `/opt/openpassword/upgrade-state/store-<id>`: the vault with its sidecars, `master.key` and `operator.token`, with owners and modes, a manifest of verified hashes and SQLite's integrity check. A missing state directory, a linked entry or a failed check aborts before the candidate starts. The path of the copy and of the state directory are journaled before the candidate runs, so recovery works even when the live directory is momentarily absent. The committed record keeps them too, so an interrupted forward recovery rewrites `previous.json`. Before the point of no return, a failed activation restores the previous symlink, the exact base unit contents and that copy. The restore stages and verifies a replacement against the manifest beside the live directory, then swaps it in, so a damaged copy leaves the live directory alone and an interruption can be repeated. The journal records the restore as done before the old release starts, and the copy is deleted only after that record, before the journal is cleared, so recovery never restores over writes the old release has accepted and an interrupted run can still delete the copy. An interrupted transaction is recovered the same way before another switch. Moving to a release that does not enforce host proof (one without `server/hosts.ts`, such as 0.3.1) is refused, for `--rollback` and `--install` alike, while any active host-bound grant or unredeemed host-bound enrollment token exists, because those would become plain bearer credentials. The message gives the counts. The check runs once up front for a quick refusal and again after the services have drained and stopped, so a grant created during the drain is still caught; the old release is then restarted unchanged. Revoke them in the console (Workspace → access grants), then retry. The updater does not revoke them itself. The last successful activation keeps its copy and `previous.json` names it. `--rollback` does not restore it, because the newer release has written since; restoring it discards that data, so do so only by hand and knowingly. The copy holds the same secrets as the vault: it stays root-only and needs the same custody as a backup. The previous release must honor `OPENPASSWORD_PORT`, which every release since 0.1.0 does, for a manual `--rollback` to prove it privately. A manual `--rollback` after a successful activation assumes a backward-compatible database. Keep a protected vault backup for a migration that changes that assumption. Updating the workstation CLI remains a separate `sh deploy/update-client.sh` operation.

### Trace a grant to its credential

Open a vault item and choose **Use for a provider connection**, or choose a saved item while adding or rotating a connection. This creates an explicit reference. Existing connections using directly entered credentials or OAuth keep their existing credential. OpenPassword never infers links from a matching name or secret.

From the connection, open **Credential and agent access** and choose **Give an agent access**. Select the agent’s operations and duration. Model access also needs a model lease. The grant list shows the stored expiry, allowed operations, connection and credential source. Follow either link to inspect it. Revoking the grant removes that agent’s access. Rotating a connection changes the source used by all its grants. Deleting a referenced item requires replacing its connection sources or revoking those connections first.

Workspace vault items keep their existing human reveal policy. A grant authorizes provider operations through the gateway. It conveys no permission to reveal or copy the underlying vault value. Lists show relationships visible to the signed-in profile.

## Remote operator and CLI enrollment

On a systemd installation, `openpassword setup-code --ssh operator@host` uses the SSH host key already verified by the operator and noninteractive sudo permission to read the service token. An SSH config alias supports custom ports and jump hosts. If sudo needs a password, log in interactively, then run this on the host:

**Run as:** an administrator with sudo · **Where:** a shell on the server · **sudo:** yes, to read the token only

```sh
sudo cat /var/lib/openpassword/operator.token | /opt/openpassword/current/node/bin/node /opt/openpassword/current/public/openpassword-cli.cjs setup-code --operator-stdin
```

A user installation can run `openpassword setup-code` on its host as its service owner (no sudo), with its existing OPENPASSWORD_HOME and OPENPASSWORD_PORT settings. A remote user installation can use `--ssh operator@host --user` when these settings and the executable are available to the noninteractive SSH shell. Enter the code only at your deployment's known console origin. Generating a new code invalidates the previous code. A canceled social enrollment needs a fresh code. Complete account setup, enroll the host under Workspace → CLI hosts, then approve each agent request under Access grants.

## Vault threat boundary

The broker encrypts each sealed value with a new random 256-bit data key. AES-GCM authenticates the value and its context, and the broker wraps the data key under the installation master key. Item titles, usernames, ownership and audit metadata remain readable in SQLite. A stolen running broker or a copy of both the database and master key can expose stored values. CLI device access and refresh tokens are stored in a per-user SQLite file on the client. Restrict access to that OS account.

This release uses server-side decryption for unattended gateway calls. A phishing-resistant login, a device remembered for a limited time, and a client-held vault decryption key address separate threats. The personal Private vault has an independent client-held key. Its owner can explicitly delegate a credential copy to the gateway. Device enrollment with passkeys and persistent 30-day unlock remain future work. The root key files must be regular, single-link files owned by the broker, readable only by that identity. Verify permissions after restoring backups.

### Protect a database backup with a separate wrapping key

Provision a random 32-byte key encoded as 64 hexadecimal characters from your secret manager. Keep a recoverable copy independent of the host and its backup destination. Mount it as a private file owned by the broker, outside OPENPASSWORD_HOME. Set OPENPASSWORD_WRAPPING_KEY_FILE to its absolute path. For systemd, an encrypted service credential can be supplied with LoadCredentialEncrypted and referenced in the environment as `OPENPASSWORD_WRAPPING_KEY_FILE=%d/vault-wrap`. The environment contains only a path. A new vault uses the wrapping key on creation.

For an existing vault, on the server, verify a recoverable backup first, then stop the broker (needs sudo). Under its service identity with both variables set, run `node deploy/wrap-master.ts` from the candidate release. With a systemd dynamic user, a one-time ExecStartPre using the bundled Node and absolute script path runs with the correct identity and credential mount on restart. The command replaces master.key atomically, leaves the database unchanged, and verifies an already wrapped file on retry. Installations with external wrapping fail to start if given an unwrapped master key. A wrapped installation requires the correct wrapping key after restart or restore. Older releases cannot open it.

Existing backup and restore scripts carry the opaque master.key file. Future snapshots contain the wrapped master key. Old backups may still contain the original unwrapped key and must retain their independent backup protection. A filesystem snapshot of the entire machine may include both credentials depending on how the external key is provisioned. A running broker still decrypts authorized values. Validate backup recovery with the separately held key before relying on this mode.

For client updates, on each workstation as the account that uses the CLI (no sudo), run the installer from a verified release and set OPENPASSWORD_CLI_SHA256 to the CLI bundle digest from an independently authenticated release manifest. The installer checks this digest before executing the downloaded JavaScript. A checksum downloaded alongside a bundle from the same server only detects mismatched downloads.

## Enroll an agent host and approve its agents

Workspace → CLI hosts issues a ten-minute, single-use enrollment ticket for a named machine. Enrollment registers a fresh Ed25519 public key. It authorizes the host to request grants. It grants no provider operations. New workspaces in the deployed service require host-bound grants from the outset. On upgrade, workspaces with existing grant history transition on first successful host enrollment. These rules include token refresh. Existing standalone clients must re-pair. Other workspaces retain their existing policy. Revoking the final host keeps this policy enabled.

Install the verified CLI and Node 24 on the agent host. Run the bridge as a dedicated service identity. The sample Linux unit in deploy/host uses a user named openpassword-host and a group named openpassword-agents. Give agent OS accounts membership in that group. Keep the identity directory owned by the service user with mode 0700. Place the verified executable at /usr/local/bin/openpassword. Put OPENPASSWORD_BROKER=https://your-console.example in /etc/openpassword/host.env. As the host administrator:

**Run as:** an administrator · **Where:** the agent host, in a verified release checkout · **sudo:** yes (shown per line)

```sh
sudo install -d -m 0700 -o openpassword-host -g openpassword-agents /var/lib/openpassword-host
sudo -u openpassword-host env OPENPASSWORD_BROKER=https://your-console.example OPENPASSWORD_HOST_HOME=/var/lib/openpassword-host /usr/local/bin/openpassword host connect
sudo install -m 0644 deploy/host/openpassword-host.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now openpassword-host
```

Paste the web ticket at the hidden CLI prompt. The service only exposes a Unix signing socket. Its private key stays in the host service account. In each agent's own OS account:

**Run as:** the agent's OS account · **Where:** the agent host · **sudo:** no

```sh
export OPENPASSWORD_BROKER=https://your-console.example
export OPENPASSWORD_HOST_SOCKET=/run/openpassword-host/bridge.sock
export OPENPASSWORD_AGENT=codex-project-a
openpassword host status
openpassword pair
openpassword whoami
```

While pair waits, a human opens Access grants, chooses Issue grant, matches the displayed request ID, agent and host, then selects the connection, operations and expiry. Refresh the page for new requests. Repeat for each agent. Pass the same three environment settings to the CLI's MCP process. Use separate OS accounts for mutually untrusted agents. Profile names select token records within one account. Another process running under the same UID can read them. Use openpassword forget to clear an obsolete local profile and use the web console to revoke its grant. Revoke an enrolled host before replacing a lost key or re-enrolling that machine. Host credentials identify a service installation; a copied private key can impersonate it. Hardware-backed attestation is outside this implementation.

Host proofs bind the broker origin, verb, path and query, authorization header and body digest to an Ed25519 signature with a timestamp and single-use nonce. The broker checks the agent grant and current host status on authorized calls. Keep clocks synchronized. Previously accepted provider calls can finish after revocation. The CLI and its MCP server produce these proofs. Raw bearer-only model clients cannot call a host-required workspace directly.

## Personal private vault

Open Private vault, generate a private vault key, confirm the saved copy and choose a separate vault passphrase. New vaults require both factors. To upgrade a legacy vault, the owner unlocks it in the browser and selects **Upgrade vault protection**. Save the new key and passphrase separately. After the vault locks, reopen it with both and check an item. Keep the old key for historical backups. A concurrent edit requires a fresh attempt. If the connection drops near commit, reopen the page. A passphrase prompt identifies the upgraded vault. Pending CLI deposit receipts must be reissued after migration. Upgrade every broker before enabling this flow. The updated root installer refuses an older broker without generation checks once a vault has migrated. Run the updated installer for both installation and rollback. A downgrade requires a separately rehearsed restore of compatible state and accounting for writes since backup. This recovery key is independent of social or password sign-in. Each human profile has a separately scoped encrypted directory in each workspace. Item names and values are encrypted in the browser using Web Crypto AES-GCM with independent random 96-bit IVs, and workspace, human profile, field and item identifiers as authenticated context. The service stores ciphertext, opaque IDs, revisions and delegation relationships. The browser unlocks directory entries and decrypts secret fields for reveal, edit or confirmed delegation. The private vault locks on page hide, navigation and after five minutes without keyboard or pointer interaction. There is no persistent device unlock or server recovery for a lost key.

Authorize gateway copy explicitly creates a personal provider connection. The browser decrypts only that item and seals its value to the broker's intake key. A human must separately authorize each agent. Editing the private item does not rotate an existing gateway copy. Revoke the connection in Connections before deleting the private source. Other workspace members, including its administrator, cannot list the private profile's items through the API. Existing shared vault items retain their previous server-side encryption and sharing. A malicious browser extension, modified JavaScript from the web server, or a compromised unlocked endpoint can still capture private data. No production security audit is implied.

The CLI saves its full host identity before exchanging the ticket. If a successful enrollment loses its response, start the bridge and run `openpassword host status` to confirm the registered ID. For a rejected or expired ticket, revoke the unused host entry and remove its identity file under OPENPASSWORD_HOST_HOME before enrolling the replacement. Keep that directory private.

Before rolling back to a broker that predates host checks, revoke every host-bound grant on the current release. An older binary cannot enforce the host signature requirement on tokens it recognizes. Private encrypted items require a compatible client to open.

### Boundaries of the first-administrator code, the private vault and local agent accounts

- **First-administrator bootstrap.** Until the first setup ticket exists, the host operator token (`operator.token`, readable only by the broker identity and root) also redeems as the setup code and at the legacy sign-in. Once a ticket is issued, only the ticket works there, it expires after ten minutes, and a new one replaces it; after the first administrator exists neither path opens. Keep the token private and issue a ticket with the SSH setup command before exposing a new installation.
- **Private item freshness.** A private item's encryption binds its content to the tenant, profile and item, which gives confidentiality and authenticity. It does not let a client detect that the server returned an earlier valid version of the same item. The revision supplied with a write only prevents concurrent overwrites. A guarantee against rollback would need a version record the server cannot rewrite, which this release does not have.
- **Local agent attribution.** The host bridge signs requests for the enrolled host with a socket that is group-accessible, so any account in that group can obtain a signature. The signature attests to the host and the request fields, not to the OS account that asked. The broker's audit therefore attributes a call to the host and the grant, not to a local account. Use separate hosts, or socket directories with separate groups, for agents that must be told apart, and verify the key-file and socket permissions on each.

For an operator-managed backup with resumable ciphertext delivery, a persistent job ID and a restore verdict, see [Recoverable operator backups](engine-operations.md#recoverable-operator-backups). The existing one-shot backup and check commands remain available.
