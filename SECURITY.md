# OpenPassword security review

Candidate based on release 0.4.1, commit 30663f9. The protected assets are human vault plaintext, gateway provider keys, host identities, agent grants, backups and release keys. The adversaries considered include a stolen database or backup, a stolen agent token, another agent on the same host, a compromised update origin and accidental disclosure during operations. A compromised unlocked endpoint or a malicious server supplying modified browser code can capture secrets entered there.

## Baseline findings through 0955152

The human vault and gateway custody section below records the subsequent changes and their limits.

| Area | Finding and candidate behavior | Evidence and residual exposure |
| --- | --- | --- |
| Sign-in and sessions | First-owner setup requires the host-issued setup code. Human login, host enrollment and individual grant approval are separate. Added rejection of cross-site browser mutations. Human sessions are server-side with expiry and HttpOnly cookies. | Console-auth and setup tests. A stolen active session can act within its role. The browser still needs separate secrets to decrypt a new private vault. |
| Machine enrollment and grant signing | Retained one-use web ticket, Ed25519 host key, time window, nonce replay protection and grants bound to the enrolled host. Agent tokens carry independent scope and expiry. | Host-private and HTTP tests cover mismatched hosts, replay and revocation. Agents sharing an OS account share its trust boundary. Check Unix socket permissions on each staging host. |
| Personal vault | Legacy private vaults relied on a single portable key. The new browser creation flow requires a random 256-bit saved key plus a separate passphrase. PBKDF2-HMAC-SHA256 with 600,000 iterations derives a nonextractable AES-GCM vault key. New or edited items encrypt the secret with a fresh random AES key. The outer vault-key ciphertext wraps that key and title, bound to tenant, profile and item context. | Wrong-factor, wrong-profile, wrong-field and legacy tests. Legacy records remain readable. No automatic rekey of old vaults, passphrase reset or account recovery. Both factors are required on every unlock for the new format. Older clients require an update to read it. Ciphertext lengths and access timing remain observable. |
| Model gateway | Grant and connection were checked before sending. Added a fresh grant, dispatch and connection-revision check before returning buffered data and before releasing streaming chunks. | The in-flight revocation test suppresses a completed provider response. Bytes delivered before revocation and an upstream charge cannot be recalled. Explicit delegation gives the gateway a decryptable provider credential. |
| Public /v1 | Keep the broker and console on loopback behind the configured ingress. Publish /v1 directly through the reverse proxy, preserving per-source and per-grant controls. The new deposit endpoint is source limited. | HTTP and rate-limit tests. Ingress path filtering and trusted proxy addresses are a staging responsibility. No Cloudflare proxy is required or assumed. |
| Backup and restore | Preserve operator-held age private key, public recipient on the host, memory-backed staging and allowlisted restore. The host runs the live service and can read gateway data while operating. An operator backup cannot reconstruct a forgotten personal vault passphrase or saved key. | See backup-age-test and backup-age-systemd-test. Verify a recovery on an isolated operator machine. A local root-owned upgrade rollback copy has a different exposure from an exported age backup. |
| Root updater | Existing updater checks an independently authenticated gate digest, stages the release, drains, verifies readiness and can restore its snapshot. Recovery now rejects symlinks, non-root ownership and group/world write access along the installed runtime path. Child-process stderr is omitted from updater exceptions. | Upgrade recovery tests and shell syntax check. A gate-approved release can execute as root. A real systemd rehearsal and independently validated gate key/digest are required before production. |
| CLI updates | A same-origin checksum alone formerly sufficed. Installation now requires a separately provisioned Ed25519 public key or an independently pinned exact SHA-256. With a public key configured, missing or invalid signatures fail before downloaded code executes. Package creation checks the detached signature against the exact CLI bytes. | Installer test checks missing trust, signed success, changed bytes plus changed same-origin checksum, and preservation of the old executable. A signature alone permits replay of an older valid release. Set the exact digest as well when targeting a particular version. |
| Supply chain | The age audit found 26 too-recent versions in the inherited lock. The candidate resolves the full registry graph at a 14-day cutoff, verifies exact publication dates before gate installation and requires integrity for downloaded packages. Bundled dependencies inherit their enclosing tarball integrity. | Run the age checker on the gate. It fails closed if registry metadata is missing. Age and integrity do not establish package safety. Review changes, install hooks, the bundled Node pin and signature provenance. |
| Logs and telemetry | CLI deposit prints a fixed acknowledgement. New audit events contain an internal item ID. Removed raw child stderr from updater failure messages. The HTTP example and audit fixtures use synthetic values. | Inspect actual reverse proxy, systemd, APM and shell tracing settings with a synthetic canary. Agent outputs for explicitly authorized operations are visible to the invoking harness. No production log audit is claimed. |
| Blind CLI deposit | Owner unlocks their private vault, enters the item in the browser and issues a five-minute receipt for that exact sealed item. The CLI accepts only the receipt on stdin. Redemption atomically consumes its digest and inserts the ciphertext once. Checks include owner session expiry, tenant, member activity and item uniqueness. | Deposit test checks authentication, replay, logout invalidation, ciphertext and CLI stdout. Receipt possession permits delivery only. A party already holding the source plaintext necessarily sees it. Pending ciphertext is cleaned on later issuance; the expiry check applies on every redemption. |

## Relationship to the supplied white paper

The operator supplied *1Password Security Design White Paper*, release 0.5.3, October 28, 2026. Chapters 3–5 and 8 distinguish authentication from decryption and explain how two independent secrets protect against an offline copy. Chapters 6–7 describe sharing and chapter 9 covers trusted devices. OpenPassword adopts the two-secret and key-separation principles for newly created browser vaults. Its KDF format, sign-in protocol and sharing model are its own. It has no claim to 1Password protocol compatibility, SRP, audited cryptographic equivalence or protection against a malicious browser update. Legacy owners can now opt into the same two-secret format. The browser verifies each re-encrypted item before staging ciphertext. The broker binds staging to the human session, expires it after one hour and rejects commit if the vault changed. A single SQLite transaction switches the vault and invalidates pending deposit receipts. Earlier backups and preexisting gateway copies retain their prior protection. Independent review and staging restore rehearsal remain outstanding.

The broker, web app, CLI and new security code are TypeScript, with existing shell deployment glue. The rebased harness delivery includes Python consumer examples for Python-only frameworks. They are excluded from the installed service runtime. First-party packages in this candidate are marked AGPL-3.0-only and retain the historical MIT notices. Reviewers should confirm release authority and third-party notices before publication.

## Human vault and gateway custody review

The new candidate adds the following protections. The operating procedures and acceptance criteria are in [Security operations](docs/security-custody.md).

| Exposure | Protection | Remaining trust or limitation |
| --- | --- | --- |
| Stolen console session | Enrolled profiles must verify a passkey for every console change except session handling, the approval ceremony, routine private-vault writes and the sealing ticket before a connection change (the list is `approvalExempt` in server/passkeys.ts). Confirming sign-in to a registered application asks for a passkey approval on the confirmation page. Removing a passkey discards that profile's pending approvals. The broker consumes a two-minute challenge and binds one approval to the session, workspace, method, route and body. Existing password replacement checks the current password. | Initial passkey enrollment requires a configured password. Committing a legacy private-vault upgrade needs approval. Profiles without passkeys retain the original approval flow: before the first passkey is enrolled, a session obtained with a member token, a password, a social sign-in or first-time setup can make these changes with no further verification. Password and social login remain available after enrollment. No SRP or PAKE implementation. The authenticator verifies the origin and user presence/verification. The browser displays the action. |
| Shared human credential | Fresh AES key per shared revision, wrapped with recipient RSA-OAEP/SHA-256. The recipient private key is encrypted under the personal vault key. Context binds the item, revision, owner, workspace, recipient, expiry and share ID. | The owner verifies the recipient card outside the service. Attribution of the sender still relies on the service. The server can see sharing relationships. Read access delivers a copy. Owner-managed read groups use an independently wrapped copy for each verified recipient. Roster changes end delivery of the previous group shares. Groups operate on item snapshots rather than a common evolving multi-writer vault. |
| Forgotten vault factors | An offline code encrypts a recovery file in the browser. A custodian can receive an encrypted envelope containing only the recovery code. | The pair recovers the derived vault decryption key. The file contains neither the saved key nor the passphrase. Keep custody of the parts separate. A copied kit cannot be recalled. A restored vault must match the original origin, workspace, profile and vault check. This mechanism does not recover account sign-in. |
| Lost device | Ciphertext on the browser is bound to a locally user-verified WebAuthn PRF, device enrollment, vault and expiry. The official client checks the active enrollment online before unlock. | A modified client on a compromised endpoint may bypass online policy if it has the local data and can invoke the authenticator. Browser storage deletion removes the local wrapper. No remote erase. Physical authenticator compatibility needs staging tests. |
| Compromised model router | Optional separate upstream OpenPassword deployment holds the provider credential. Its own grant and metering restrict use by the router. The configured upstream HTTPS origin is pinned per connection. | The independent custodian remains trusted with provider plaintext. The router sees model traffic and can spend the remaining downstream lease. No enclave, attestation or split-key protocol. Other connector types retain their existing credential handling. |
| Supply chain and browser delivery | Existing signed CLI, dependency-age gate and signed/digest-pinned deployment process; WebAuthn server verification uses a pinned library. | The web origin still supplies the code handling human unlock. A compromised web release can capture secrets. A gate signature gives provenance, not correctness. External cryptographic review, physical device tests and production ARM64 restore evidence remain outstanding. |

### Engine integration review

| Finding | Candidate treatment | Evidence or remaining exposure |
| --- | --- | --- |
| A shared journal token can read every stream | Loopback-only ephemeral listener and fresh per-epoch token. Public activity is served through broker authorization. | Engine integration test scans actual files for synthetic identifiers and secrets. Same-identity processes remain trusted. |
| Redelivery after a lost HTTP response could strand a grant | The broker seals a short-lived redemption receipt bound to the attempt, code and current grant. | Forced process restarts, equivalent response, revoked-grant refusal and legacy one-use tests. Encrypted expired receipts are pruned on redemption. |
| Worker downtime could delay a revoke | The request path checks the committed grant record. The worker propagates invalidations. | Real HTTP refusal measured after the revoke response. In-flight upstream effects still need reconciliation. |
| Backup or rollback could restore mismatched stores | Broker intents, accounting and display cursors share the vault image. Engine epoch data is reconstructed. | Local snapshot and encrypted restore exercises. Native ARM64/macOS execution and real systemd staging remain release gates. |
